The small business build playbook

Which tool to reach for when a small business needs custom software — web apps, mobile apps, internal tools, public sites. Written for someone who prompts AI fluently and doesn't write code, and who has to live with the consequences of the choice.

The one rule

Build the thing that makes the business different. Buy everything else — especially anything that, when it breaks, costs the client money or puts them in front of a regulator.

Almost every expensive mistake in this space is a violation of that sentence. Someone rebuilds bookings, invoicing, rostering or payments in an AI builder because the demo looked easy, then spends six months maintaining a worse version of a product that costs $30 a month.

Before the tools

Triage, in order

Tool choice is the fourth question, not the first. Work through these in sequence — each one gates the next, and most projects die on question two.

Does this software need to exist?

A large share of small-business "app" requests are a spreadsheet problem, a settings change in software they already pay for, or a process problem that software will encode rather than fix.

Kill criterion: if you can't name the specific decision or task the software removes, stop. Build nothing.

Does it already exist as a product?

Bookings, invoicing, CRM, rostering, e-signature, inventory, email, payments, scheduling, forms. These are mature categories with $10–50/month products that have absorbed a decade of edge cases you have not thought of.

Kill criterion: if a product covers 80% of it, buy the product and build only the missing 20% around it. Integration beats reimplementation nearly every time.

What kind of software is it, really?

There are four archetypes and they have almost nothing in common technically. Getting this wrong is what makes people pick a tool that fights them for months. See the next section.

Test: who uses it, how often, do strangers find it through Google, and does it touch money or personal data?

Who owns it in two years?

Ask this before you write a prompt, not at handover. Can the client take it elsewhere? Can you walk away? Can a different developer pick it up? Some tools give you a real codebase; others hold your work hostage in a proprietary editor.

For client work this is the deciding criterion, ahead of price and ahead of build speed.

Question three, expanded

The four archetypes

Sort the project into one of these before choosing anything. The right tool for a public marketing site is close to the worst tool for an internal ops app.

Archetype A

Public site

  • Strangers arrive from Google
  • SEO and page speed are the product
  • Content changes often, logic is thin
  • No login for most visitors

Reach for: Webflow. Lovable is now viable too — it gained real server-side rendering in May 2026, which was the thing that used to disqualify it here.

Archetype B

Internal tool

  • Staff only, known users, everyone logs in
  • SEO irrelevant, rendering irrelevant
  • CRUD, forms, dashboards, approvals
  • Ugly-but-working is acceptable

Reach for: Base44 when you want database, login and email handled for you; Lovable, Bolt or Replit when you want the code to stay portable.

Archetype C

Customer-facing transactional

  • Strangers create accounts and pay you
  • Holds personal data, payment records
  • Multi-user state, race conditions, refunds
  • Failure has financial or legal cost

Reach for: a bought engine wherever the category exists. Where it doesn't, this is the archetype that justifies real code — Claude Code or Cursor with Next.js. Highest risk

Archetype D

Native mobile

  • Genuinely needs the device, not the browser
  • Used repeatedly by the same people
  • Store listing actually matters
  • Offline, background, or hardware access

Reach for: FlutterFlow or Expo. But first read the mobile section — most requests that arrive here belong in A or B.

The expensive misunderstanding

How these tools actually bill you

Three billing models, and the difference matters more than the headline price — particularly if you quote clients fixed prices.

  • Flat subscription (Webflow, most site builders, Claude Code, Cursor). Predictable. Quote with confidence.
  • AI credits (Lovable, Bolt, Replit). You pay per generation attempt, not per result. The failure mode is a debugging loop where each fix breaks something adjacent and every retry costs. A modest app with authentication and a database can consume more than a month's allowance in one build session. Top-ups typically cost roughly double the in-plan rate.
  • Split credit pools (Base44). Two meters, and they behave differently. Build credits are spent while you develop and stop when you stop. Runtime credits are consumed by the live app every time it sends an email, calls a model or accepts an upload — so the bill tracks your client's usage, not your effort, and it keeps running long after you've handed over.
  • Metered agent time (Devin's ACUs). You buy the agent's working time, not its output. An ACU is roughly a quarter-hour of active work at somewhere near $2.25, so an hour of Devin sits around $9 whether the attempt succeeded or not. A task the agent misunderstands and grinds at costs the same as one it nails.
If you bill clients fixed-price Any meter transfers an unbounded variable cost onto a fixed-price engagement — but note which side of the handover each one sits on. Build-time meters (AI credits, agent ACUs) threaten your margin during the project and stop when you ship. Runtime meters threaten the client's operating cost forever, and they are the ones to put in the client's name before launch. Price in a ceiling for the first kind; transfer ownership of the second.
The other way to use an agent

Devin, and delegated coding

Devin belongs in a different column from everything above it. It isn't a builder you assemble an app in — it's an autonomous engineer that works in a real repository. That puts it in the same family as Claude Code and Cursor, and the family resemblance matters less than the one difference.

Claude Code and Cursor are supervised. They run where you are, you watch each change land, and you interrupt the moment it goes wrong. Devin is delegated. You hand it a scoped ticket, it works asynchronously in its own cloud machine with a shell, editor and browser, and it returns a pull request. You review the result, not the process.

That single difference sets both the appeal and the risk. Delegation is what lets you run several tasks at once without being present for any of them. It is also what removes the correction step that keeps a supervised agent honest — a misunderstanding at minute two is still being built on at minute forty, and you pay for every one of those minutes.

Where it earns its keep
  • Work you can specify precisely before it starts — a bug with a clean reproduction, a library upgrade, backfilling test coverage
  • Repetitive changes across many files where the pattern is known
  • An existing codebase with conventions to imitate
  • Queued work you genuinely don't want to sit and watch
Where it doesn't
  • Anything ambiguous. Reported success drops sharply as specification quality drops, and small business requirements arrive vague by default
  • Greenfield projects with no conventions yet established
  • Cross-cutting changes touching many interdependent files
  • Solo operators — review capacity, not writing capacity, is usually the bottleneck, and delegation adds to the side you're already short on

The honest verdict for small business work: Devin is a complement to a supervised agent, not a replacement for one, and it's the harder of the two to justify. It rewards a clear specification and a codebase worth imitating — exactly the two things a new client project doesn't have yet. Reach for it once the project is real, the conventions exist, and the backlog is full of well-defined chores. Not on day one.

Lower confidence Cognition's own pricing and documentation were unreachable from the research environment. The $20 entry, roughly $2.25 per ACU and the quarter-hour-per-ACU figure are consistent across many secondary sources but unconfirmed at source. Published success rates vary so widely between reviewers — and the widely-quoted SWE-bench figure is from Devin's 2024 launch, not today — that no single number is quoted here. The qualitative pattern, strong on scoped work and weak on ambiguity, is what the sources agree on.

Archetype D, interrogated

The mobile app question

When a small business says "we need an app," they almost always mean "we need to work properly on phones." Those are different projects with a tenfold cost difference. Establish which one before agreeing to anything.

The default answer is a PWA

A progressive web app installs to the home screen, works offline, sends push notifications on both platforms, and costs nothing beyond the web build you were doing anyway. It keeps SEO and link sharing intact. For staff tools and for customers who transact occasionally, this is almost always correct.

What actually justifies going native

  • Background location tracking, or continuous GPS while the screen is off
  • Reliable offline-first use in the field, with sync on reconnect
  • Deep hardware access — advanced camera control, BLE, NFC, biometrics
  • Push notifications as the core product loop, not a nicety
  • The client's customers genuinely expect a store listing and will search for one

One of these, and native is defensible. None of them, and you are paying a large premium for an icon on a home screen.

Apple will reject a wrapped website — this is the exact wording Guideline 4.2, Minimum Functionality: "Your app should include features, content, and UI that elevate it beyond a repackaged website. If your app is not particularly useful, unique, or 'app-like,' it doesn't belong on the App Store." And 4.2.2: "Other than catalogs, apps shouldn't primarily be marketing materials, advertisements, web clippings, content aggregators, or a collection of links."

Verified Fetched from developer.apple.com on 4 August 2026. Rejections under this clause were still being issued and appealed on Apple's developer forums as recently as April 2026, including against apps whose developers had added genuine native features. Apple does not tell you what would satisfy the rule.

If you need a store listing anyway

  1. Capacitor — free and open source. Wrap your existing web app, get real native APIs, manage builds and signing yourself.
  2. Median.co or Natively — paid wrapper services, roughly $30/month self-serve up to low thousands for full-service submission. Median publicly claims a very high approval rate; that's a vendor claim, but it suggests a well-configured wrapper with native navigation and push usually clears review.
  3. Rebuild natively — FlutterFlow or Expo. The only option that removes 4.2 risk entirely.
  4. Store fees regardless — Apple Developer Program $99/year, Google Play $25 one-time.
The part that bites later

Ownership, lock-in and handover

For client work this outranks everything else. You are not only choosing how to build — you are choosing what the client is left holding when the relationship ends, amicably or otherwise.

  • Real code export (Lovable, Bolt, Replit, FlutterFlow, Claude Code, Cursor, Devin). The client can be handed a repository that runs. Another developer can continue. You can move hosts without a rewrite. This is the honest position to be in.
  • Export that isn't portability (Base44). You can download the code, and it will not run on its own. The front end comes out; the database, authentication and backend logic stay behind the vendor's SDK. Leaving means rebuilding the backend and migrating the live data — the export is a starting point for a migration, not an escape hatch.
  • No export at all. The work exists only inside the vendor. If the client stops paying, it stops existing. This can still be the right call for a genuinely internal tool — but say so explicitly, in writing, before you start.
The question that separates the first two Not "can I export the code?" but "if I export it and the vendor disappears tomorrow, does it run?" Vendors answer the first question in their marketing. Only the second one matters at handover. The tell is an all-in-one platform: if the database, login and file storage came free with the builder, they are the part you cannot take with you. Base44's export is a genuine convenience and a real head start — third-party SDKs exist specifically to re-point those apps at a self-hosted backend — but it is not the same product as a repository you can deploy anywhere.
Tell the client which of these they're buying. "You'll own the code" and "you'll own an account" are very different products, and only one of them survives a billing dispute.

Two practical habits: put SaaS subscriptions in the client's name with you as a collaborator, so nothing dies when your card expires or the engagement ends. And commit generated code to a repository the client controls from day one, not at handover.

Non-negotiable

The security pass

AI builders scaffold authentication that looks finished. The recurring, documented failure is that database access rules are generated incompletely or not at all — the app works perfectly because the rules protecting it were never switched on.

Verified The reference case is CVE-2025-48757, disclosed May 2025: a scan of 1,645 AI-generated projects found 303 endpoints across 170 of them — 10.3% — where database tables could be read by unauthenticated requests, because row-level security was never enabled. CVSS 9.3.

The generalisable lesson isn't about one vendor. It's that "the AI set it up" is not a security posture, and for client work it's not a defence either. Before anything holding customer data goes live:

  • Open the database dashboard and confirm access rules exist on every table, not just the obvious ones
  • Try to read a table while logged out. Actually try it.
  • Confirm no admin or service key is present in client-side code
  • Confirm secrets sit in server-side environment variables, not in the front end
  • Check what the app emails, logs and exports — leaks are as often in a CSV as in a database
The structural fix Wherever a bought product can hold the sensitive data instead of you, let it. If customer records live in an established CRM or booking platform rather than a database you scaffolded in an afternoon, their security team carries the risk instead of yours. This is the strongest argument for the buy side of the build-versus-buy call, and it has nothing to do with saving development time.
Worked example

A short-term rental direct booking business

Running one real project through the playbook, since abstractions hide the interesting decisions. A single Sydney holiday rental wanting direct bookings to escape platform commission, plus a request for iOS and Android apps.

  • Q1, should it exist? Yes — the commission saved is the whole business case.
  • Q2, does it exist already? Partly, and this is the pivotal answer. The booking engine — availability, calendar sync with listing platforms, minimum stays, deposits, damage holds, guest messaging — is a mature $16–40/month category. Building it means owning double-booking risk forever.
  • Q3, which archetype? Both A and C, which is why it's confusing. The marketing site is Archetype A and should be built. The booking flow is Archetype C and should be bought. Splitting them is the whole answer.
  • Q4, ownership? Owner-operated, so lock-in matters less than usual — but the marketing site is the SEO asset and should sit somewhere portable.
  • Mobile? No triggering requirement. Guests book once a year and will never install an app; a wrapped booking site is exactly what Guideline 4.2 targets. PWA.

Resulting stack: a built marketing site, a bought booking engine, the operator's own payment account, and no native apps — around US$65/month. The one thing genuinely worth custom-building turned out to be a compliance tracker for a local 180-day letting cap, because no product in the category does it.

Reference

Ten-second version

  1. Public site with SEO → Webflow or Lovable
  2. Internal staff tool → Base44 if you want the backend handled, Lovable or Bolt if you want the code portable
  3. Customers paying money → buy the engine; build only what's missing
  4. "We need an app" → PWA until something forces native
  5. Client work → code export is non-negotiable, and check the export actually runs without the vendor
  6. Fixed-price engagement → cap the build-time meters, hand the runtime meters to the client
  7. Delegating to an agent → only for work you could have specified precisely in writing
  8. Anything holding customer data → do the security pass before launch
